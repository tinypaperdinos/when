## Finding 1: service-level tests keep passing false coverage for Zod-layer validation

Three separate tickets shipped a round-1 `reviewer-tests` **blocking** finding with the
identical root cause: a test calls the service method directly with already-valid input,
and gets treated (including by the implementer, sometimes by name — "trims a padded
title before persisting") as coverage for behavior that's actually implemented in the
router's Zod schema, one layer up. A schema regression (dropping `.trim()`, dropping
`.nullable()`, weakening a format regex) then ships with the full test suite green.

- `task-crud` (#31): `task-service.test.ts`'s test literally named "trims a padded title
  before persisting" asserts the *un-trimmed* value was passed to `db.entry.create` —
  correct behavior for the service (trimming happens in Zod), but the name and the
  reviewer's own initial reading treated it as trim coverage. No router-level test sent a
  padded/whitespace-only title through `createCaller`. `reviewer-tests` mutation-tested
  by removing `.trim()` from the router schema: 30/30 tests still passed.
- `notes-on-tasks` (#32): `updateInput.notes` gained `.nullable()`; every router-level
  test that touched `notes` sent a string, never `null`. Mutation-tested by removing
  `.nullable()`: 50/50 server tests still passed, while a real client sending
  `{ notes: null }` (exactly what the UI's "clear notes" flow does) would get rejected
  with `BAD_REQUEST` in production.
- `shared-zod-schemas` (#35): task `create`'s malformed-`dueDate` case was only tested on
  `update` and on both event procedures, not on task `create`. Separately, the
  task/event date-nullability asymmetry (`dueDate` nullable, `date` not) — the plan's own
  named centerpiece risk of this refactor — had no router-level runtime test in either
  direction; it was only caught by `tsc`, and only incidentally (a service-level test
  literal or a null-guard in `event-service.ts` happened to also break).

Each of these cost a full extra fix round (test-only fix, verified by mutation-testing
the fix itself in round 2) that would have been unnecessary if the router-level test had
been written alongside the schema change in round 1. Added as a rule under a new
"Testing conventions" section in `AGENT_RULES.md`.

## Finding 2: new conditional logic ships without a test that can actually catch a regression in it

A related but distinct pattern, this time mostly on the frontend: a ticket adds or
changes a conditional branch, and the corresponding test either doesn't exist or asserts
something that can't discriminate the new behavior from its absence. Every instance below
was caught by `reviewer-tests` round 1 as blocking and fixed with a test-only round-2
commit — again, a guaranteed extra round that self-mutation-testing during implementation
would have caught.

- `date-time-picker` (#28): the uncheck-"Add time" handler manually rebuilds the value
  object (`onChange({ date: value.date })`); the only test for that path asserted
  `result.time` was undefined and never checked `result.date` survived. Mutating the
  handler to `onChange({} as never)` — a real, user-visible data-loss bug (unchecking
  "Add time" silently wipes the already-entered date) — left the test green.
- `form-primitives` (#25): `select.tsx`'s `defaultValue`/`value` consumer-wins-over-
  placeholder-fallback branch (itself an unplanned bug fix discovered during
  implementation) shipped with zero test coverage of that branch.
- `select-datepicker-refactor` (#40): the newly-hand-rolled `Select`'s *uncontrolled*
  `setInternalValue` commit path had no test — every existing test only exercised the
  controlled path.
- `calendar-view` (#42): the only pre-fix test for a completed-task calendar event
  asserted its title rendered, which says nothing about the `eventClassNames`
  strikethrough styling change this ticket introduced; `reviewer-code`'s own round-1 notes
  conflated the two until `reviewer-tests` pointed out the gap. Also, the one existing
  all-day-drop test used a literal `Date` whose local getters and `toISOString()`
  couldn't disagree in the CI timezone, so it couldn't distinguish "reads local getters"
  from "reads `toISOString()`" — the actual thing plan.md's fix was about.
- `design-consistency-theme-tokens` (#20): `RootRoute` had **zero** test file before this
  ticket. The ticket's one piece of new interactive logic (`activeOptions={{ exact: true
  }}`, fixing the "/" nav link staying highlighted on `/calendar`) shipped with no test —
  there was no pre-existing suite to extend, and the plan itself only said a test "should"
  be added if one is, leaving it a judgment call that both `planner` and `implementer`
  skipped.

All five are the same shape: the diff changes behavior; the test suite, either because
the touched file had no prior tests or because the new test only checks an unrelated
signal, can't tell the difference between the fix landing and the fix being reverted.
Folded into the same "Testing conventions" rule as Finding 1 (mutation-test new logic
yourself before treating it as covered), with an explicit callout for zero-prior-coverage
files since that's the sharpest version of the trap (nothing to lean on, and no existing
test to notice the gap by extension).

## Finding 3: router file-naming convention isn't written down anywhere

`apps/server/src/routers/task-router.ts` and `event-router.ts` both use the *singular*
entity name in the filename while exporting/registering the *plural* name
(`tasksRouter`/`eventsRouter`, `tasks:`/`events:` on `appRouter`). This is a real,
consistent, two-file precedent — but nothing in `AGENT_RULES.md` states it, so `tags`'
plan (#37) named the new file `tags-router.ts` (plural, matching the export) and
`plan-refiner` had to catch and fix it in round 1 (a real, checkable deviation per the
refiner's own note, not a nitpick). Cheap to write down given there are only two
data points but a clean, mechanical, and now three-times-precedented pattern (`task-`,
`event-`, `tag-router.ts`) — added a one-line rule to the Tech stack section so the next
new entity router gets it right in the plan the first time.

## Finding 4: local `main` is predictably stale in this environment

At least three separate review rounds (`notes-on-tasks` #32, `tag-input-badge` #36,
`event-crud` #33) independently discovered that the local `main` ref was pinned behind
`origin/main` — missing already-merged sibling PRs — before diffing, and each had to
manually correct it (`git branch -f main origin/main` or diffing against `origin/main`
directly) to get the right diff scope. This is pure repeated overhead: the same
discovery, made fresh by a different reviewer instance each time, with no note anywhere
telling the next one to expect it. Added a short git-ref-hygiene bullet under "Branch and
PR conventions" so future reviewers (and the orchestrator, when cutting a new branch)
check/update the local ref before computing a diff instead of rediscovering the workaround
each time.

- No ticket ever wrote `status.md` as anything but `pr-opened` at hand-off — the
  `done`-is-never-written clarification from the last audit is holding.
- No ticket hit either iteration cap (`plan-refiner` never needed a 3rd round;
  `reviewer-code`/`reviewer-tests` never needed a 3rd fix round) — the caps are correctly
  sized, no evidence they need loosening or that "stuck" is being avoided by cutting
  corners.
- The re-review scope rule (added in the first audit's PR #27) is visibly being followed:
  round-2 review notes consistently scope to the fix commit only, cite `AGENT_RULES.md`
  by name, and skip re-running lint/typecheck/build. `select-datepicker-refactor`'s round
  1 explicitly cites the reviewer-code browser-QA restriction (added in the same PR) and
  correctly declines to spin up Playwright — no recurrence of the form-primitives-era
  pattern that prompted that rule.

  code commits in every ticket checked — the "one commit, right before PR-ready"
  convention from the original pipeline setup is holding.
