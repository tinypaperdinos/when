# Audit — 2026-07-26 (first audit)

Only one ticket (`scaffold-project`, PR #3) has been through the actual `/ticket`
pipeline so far, so this is a single-data-point pass, not a cross-ticket pattern search.
PRs #1, #2, #10 were orchestrator-direct changes with no ticket folder — nothing to
audit there beyond what's already reflected in `AGENT_RULES.md`'s own edit history.

## Checked for drift first

The two prior edits to `AGENT_RULES.md` (PR #3's `review-notes-code`/`review-notes-tests`
split, PR #10's `tickets/` relocation + batched-commit rule) already captured
`scaffold-project`'s two big process lessons. No further action needed there — did not

## Finding 1: unresolved `superjson`/`Date` gap

`apps/server/src/trpc.ts` and `apps/web/src/trpc.ts` have no transformer configured, so
`Date`-typed fields (`dueDate`, `date`, `createdAt`, `updatedAt` on `Entry`) cross the
tRPC boundary as plain strings while the type inferred from `AppRouter` still claims
`Date`. This was flagged twice during `scaffold-project`:
- `refiner-notes.md` round 2 (plan-refiner)
- `review-notes-code.md` round 1 (reviewer-code)

Both times it was left non-blocking because nothing in the diff at that point called a
`Date` method on those fields. Confirmed by directly reading both `trpc.ts` files that
it's still unresolved in the codebase as of this audit — a real, live gap, not
theoretical. It's exactly the kind of landmine a future ticket's `planner`/`implementer`
would hit with no warning, since ticket-local notes aren't read outside that ticket.
Promoted to a shared rule in `AGENT_RULES.md`'s Tech stack section (kept short there —
this file has the full reasoning).

## Finding 2: `status.md`'s `done` state is never actually written

Confirmed by reading `.claude/skills/ticket/SKILL.md`: the pipeline's last write is
`pr-opened`, right before `gh pr ready` — merging is the human's job and happens outside
any agent's turn. `tickets/scaffold-project/status.md` still reads `pr-opened` even
though PR #3 is merged. Not a bug — added a clarifying note to `AGENT_RULES.md`'s Ticket
state section so a future agent doesn't "fix" this inconsistently (e.g. by having some
agent start writing `done` on its own initiative, which would be a change to the
pipeline's actual behavior, not just documentation).

## Finding 3: `reviewer-code` had no "verify by running it" instruction (since applied)

`scaffold-project`'s one blocking finding (a crashing `dev` script from tsx CLI argument
order) was only caught because `reviewer-code` chose to actually run `npm ci`, the dev
servers, and `curl` against the running server, rather than just reading the diff —
reading the `package.json` diff alone would not have caught it, since the broken line
looked plausible on paper. `reviewer-tests.md` already had an explicit "verify by
running the test suite" instruction; `reviewer-code.md` had no equivalent for
runtime/build claims despite having the same `Bash` tool.

Flagged as a proposal rather than applied unilaterally (per `meta-auditor`'s mandate not
to silently rewrite another agent's definition). Human confirmed it in the same PR (#11)
this audit shipped in — `.claude/agents/reviewer-code.md` now explicitly requires running
lint/typecheck/build/dev commands relevant to the diff. No longer an open item; this
audit file is the record of why that instruction exists.
